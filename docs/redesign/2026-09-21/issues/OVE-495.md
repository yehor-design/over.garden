## Acceptance criteria

 1. Lead with object name, owner and real photo when present; provide a meaningful link to canonical species/form as secondary reference.
 2. Use object-specific entry history and factual timeline. No empty technical provenance block above actual observations; progressively reveal relationships with clear labels.
 3. Breadcrumbs reflect owner/object relationship rather than pretending the owned object is a catalogue species. Owner Write leads to exact owned destination.
 4. Read-only guests never see executable owner mutations; claim/invitation UI uses existing server identity and authorization semantics.
 5. Render uncertain lineage as uncertain, with source/relationship details; do not imply a verified genetic or ownership fact from an unreviewed claim.
 6. Preserve permanent ASCII addresses, alias behavior, static public document and deleted-object semantics.
 7. Separate questions requiring an answer, pending claims and invitation acceptance. Show source/target object, gardener and current status using real identity, not technical IDs alone.
 8. Before accepting/rejecting/reassigning, state what relationship changes and what stays owned/public according to the backend. Do not equate a claimed relation with verified biology.
 9. Preserve signed invitation/token and server authorization contract; expired, already used, conflicting and unauthorized claims have distinct explanations.
10. Keep return intent through authentication without exposing token values in UI/analytics. No secret-bearing screenshots in receipts.
11. Use deliberate secondary placement from object provenance; no lineage actions compete with routine New entry.
12. Support long labels, related objects with same names, safe cancel, failed action and keyboard focus return.

## Proof

Compare guest and owner passport for unlinked and related objects; verify breadcrumbs, direct write context, static bytes and visible uncertainty using controlled lineage fixtures.

Fixture handoff for valid/expired/used invitation, cross-user misuse, duplicate names and failed acceptance; assert exact relationship outcome and no unsupported ownership change.

Attach exact tested SHA, behavior/file summary, screenshots and relevant gate output. Verify applicable guest/member/owner roles, UK/BG/RU long labels, narrow/wide layouts, keyboard, zoom, empty/populated and pending/error/retry states. Public changes require canonical/static/no-JS proof; workspace changes require hard-load failure proof. Mutations require acknowledged server outcomes. Register browser specs in the actual gate; automated accessibility checks do not replace manual evidence. Follow repository PR/CI/release rules, distinguishing local results from production; production test mutations require applicable authorization.
