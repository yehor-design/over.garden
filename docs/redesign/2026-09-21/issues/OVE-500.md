# Redesign communities, discussions and moderation operations

https://linear.app/overgarden/issue/OVE-500/redesign-communities-and-discussions-with-preserved-posting-context

## Outcome

A community is a coherent context for reading and contributing; its first-post action no longer drops users into an unrelated garden setup. Owner moderation and community management are clear task-oriented extensions of the same design system.

Audit traceability: OG-UX-017, OG-UX-035, OG-UX-040. Baseline: 2026-09-21, e554aec506e84ec6f8304c4704084671ed19f399. Recheck current main before editing.

Radical layout/IA/page regrouping is authorized. Threads leads the light visual system; [vc.ru](<http://vc.ru>) provides the centered three-column group and relevant reading/social patterns; Airbnb informs progressive setup. Phosphor is the sole UI icon library. Thiings selection/use is unrestricted by owner direction, with no purchase or license-review gate; provider facts are recorded honestly in the contract. ## Acceptance criteria

 1. Directory cards and detail header explain topic, community identity and actual supported membership/contribution actions. Use [vc.ru](<http://vc.ru>) topic attribution/navigation mechanism while retaining Threads styling.
 2. Community Write carries exact community context through sign-in and supported contribution composer; do not silently turn a discussion into an owned-object entry. If entries can be shared, preserve one original identity and existing association rules.
 3. Show current discussion list, author/date, relevant community information and clear empty-first-contribution state. Right rail supports this community rather than generic welcome content.
 4. Discussion detail reuses readable post/comment controls while respecting its own entity and canonical URL. No unsupported ranking or moderation capability invented.
 5. Move community management to appropriate owner/account context with role checks and purposeful settings; no admin panel recreation.
 6. Verify back navigation, guest entry points, deleted discussions, forbidden contribution and partial errors.
 7. Show content context, author, reason/state and actual available action before changing moderation state; avoid unlabeled icon-only destructive actions.
 8. Separate queue filtering, item review and community settings into meaningful sections. Preserve exact comment/discussion/community identity when moving between them.
 9. Confirm destructive consequences where required, keep cancel and retry safe, prevent double submission and reconcile actual server result.
10. Guest/ordinary member cannot read protected content or perform owner mutations even when copying a URL or submitting a forged form.
11. Provide empty queue, loading, failed row and failed list states; preserve filter/scroll on action and do not hide unrelated rows after one error.
12. Use Phosphor, semantic tables/lists, accessible menus and responsive controls; reuse community public context without exposing private moderation metadata.

## Proof

Guest→sign-in→same community intent, member post in seeded environment, comments and directory/detail/back across locales. Assert submitted community ID and absence of accidental garden-object creation.

Controlled owner review, failed action, duplicate submit and ordinary-member forged request tests; keyboard and mobile populated queues with exact server-state readback.

Attach exact tested SHA, behavior/file summary, screenshots and relevant gate output. Verify applicable guest/member/owner roles, UK/BG/RU long labels, narrow/wide layouts, keyboard, zoom, empty/populated and pending/error/retry states. Public changes require canonical/static/no-JS proof; workspace changes require hard-load failure proof. Mutations require acknowledged server outcomes. Register browser specs in the actual gate; automated accessibility checks do not replace manual evidence. Follow repository PR/CI/release rules, distinguishing local results from production; production test mutations require applicable authorization.
