## Acceptance criteria

 1. Reduce consent obstruction using an accessible responsive placement. Preserve the existing requirement that undecided visitors see the notice on every page until a choice; no silent acceptance or hidden rejection.
 2. Choice controls remain equally understandable, keyboard reachable and usable at 320px/zoom. The overlay must not cover focused primary content indefinitely; test mobile safe areas.
 3. Privacy/disclosure/support follow reader-oriented typography and corrected factual content from task 02. Link to detailed explanations instead of showing database/queue jargon in the main flow.
 4. Erasure request describes scope, current retention and actual receipt/status; distinguish deleting an entry from erasing account-associated data and external cached copies.
 5. Keep token/verification failure, pending, accepted and completed states honest. Do not implement a destructive schema or bulk purge under UX authorization.
 6. Preserve consent-based analytics exclusions and first-publication acceptance logic.
 7. List requests with appropriate minimal identity, received date, verification state and next permissible action; keep sensitive details limited to needed role-protected views.
 8. Explain queue/processing/completed/failed state in plain language. Technical references may be available as secondary diagnostics rather than primary instructions.
 9. Destructive confirmation must describe actual scope; never implement bulk purge or destructive schema changes under redesign authorization.
10. Retry follows existing idempotent lifecycle and does not manufacture completion. Preserve audit receipts and retention behavior.
11. Cover empty/populated/error states, keyboard action flow, mobile tables and owner-role rejection for ordinary members.
