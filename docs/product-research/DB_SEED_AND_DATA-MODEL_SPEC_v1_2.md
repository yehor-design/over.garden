## §2. Продуктовий контекст (навіщо каталог існує)

OverGarden — платформа доказових журналів: **користувач → простори → об'єкти → журнали**. Об'єкт (грядка з помідором, вулик, дерево, тварина) має «паспорт», ключове поле якого — **сорт або порода**.

**Каталог сортів/порід — це ключ-з'єднання між користувачами.** Якщо дві людини, які ведуть той самий сорт, посилаються на той самий запис каталогу, виникає мережевий ефект: спільний перегляд, порівняння результатів, соцграф «усі, хто веде цей сорт». Якщо ж вони пишуть назву по-різному (різні написання, мови, народні варіанти), вони не з'єднуються — і цінність руйнується.

**Стратегічний наслідок (визначає архітектуру):**

- Шар **народних/регіональних назв сортів** — це рів продукту (його не можна купити, він будується спільнотою).  
- Решта (види, офіційні сорти, породи) — стабільний кістяк, який береться готовим.

**Локалі:** Україна (UA) та Болгарія (BG), обробляються паралельно й окремо. Мови назв: українська (uk), російська (ru), болгарська (bg), англійська (en), латина (la).

**Режим використання:** локальна копія каталогу має працювати без мережі для offline-capture сценарію («вила» / поле без зв'язку) з подальшою синхронізацією. Це НЕ означає offline-first архітектуру всього застосунку: продукт лишається online-first + Dexie/IndexedDB локальна черга записів/фото (`TECH_STACK_DECISIONS §2.8`; `OverGarden_MVP_PRD_v0.md S10`).

## §3. Архітектурний огляд

**Модель — гібрид із трьох частин:**

1. **Придбаний кістяк (acquire).** Завантажуємо з безкоштовних чистих джерел і зберігаємо у власній БД: види, офіційні сорти, породи. Майже статичний; оновлюється рідко плановим ре-синком.  
2. **Збудований шар (build).** Народні назви сортів і довгий хвіст рідкісних/спадкових сортів. Нема в жодному готовому джерелі; росте через користувачів (UGC) \+ курування. Живий, безперервний.  
3. **Двигун зведення (matching).** Робить так, щоб попри помилки, різні мови й варіанти написання різні люди потрапляли на один запис. Стек двигуна — у `MATCHING-ENGINE_STACK_SPEC.md`; як він лягає на модель даних — §8.

**Принцип володіння.** Дані копіюються у власну БД; від зовнішніх API наживо не залежимо (дані стабільні). Біля кожного запису зберігається **ID джерела** — для майбутнього ре-синку, звірки й провенансу.

**Потік даних (високорівнево):** `Зовнішнє джерело → завантаження легальним каналом → парсинг → нормалізація назв (+ ключі матчингу) → дедуп проти наявного → запис у схему з провенансом і source-ID → індексація в пошуковий рушій → доступний для typeahead`. Паралельно: `Користувач/агент → створення з гейтом → статус «непідтверджено» → черга курування → підтвердження/злиття`.

**External-source breadth.** Ingestion should capture the maximum legally reusable source payload into raw/source snapshots, including occurrence/distribution metadata and coordinates when source terms allow it. These fields are not canonical product location data by default: keep them isolated with provenance, license, source-version, checksum, and usage flags, then expose only deliberate safe projections. User-supplied garden/journal/media data remains governed by the v0 no-precise-user-location rule.

## §4. Модель шарів (build vs acquire по кожному)

Кожен запис каталогу належить одному або кільком логічним шарам. Шари — це не окремі таблиці, а ролі даних (фізична схема — §7).

- **Шар A — Видовий кістяк.** Перелік видів/таксонів із науковими назвами та ієрархією. *Підхід: ACQUIRE.* Джерела: Catalogue of Life, World Flora Online, GBIF.  
- **Шар B — Народні назви видів (вернакуляр).** Локальні назви видів (uk/bg/ru). *Підхід: ACQUIRE частково \+ BUILD доповнення.* Джерела: EPPO, Wikidata, GBIF vernacular; прогалини закриваємо власною локалізацією.  
- **Шар C — Канонічні сорти.** Офіційно зареєстровані сорти культур. *Підхід: ACQUIRE.* Джерела: Держреєстр UA (готово), IASAS BG \+ EU Common Catalogue (парсинг).  
- **Шар D — Канонічні породи.** Породи тварин. *Підхід: ACQUIRE кістяк \+ BUILD локалізація.* Джерело: VBO (англ/лат, локалізуємо самі); нехребетні/бджоли — невеликий список вручну (звірений з DAD-IS).  
- **Шар E — Аліаси/синоніми сортів (народні, мовні, орфо).** *Підхід: BUILD (рів).* Джерела: ручний засів топ-100–200 культур (AI пропонує → людина звіряє) \+ UGC \+ згенеровані варіанти.  
- **Шар F — Двигун зведення.** Пошук, нормалізація, транслітерація, fuzzy-match, дедуп. *Підхід: ACQUIRE (permissive open-source).* MVP-мінімум: Meilisearch \+ ICU (+ власний fold-шар) \+ cyrtranslit \+ RapidFuzz \+ унікальний індекс. Повний стек і призначення кожного інструмента — `MATCHING-ENGINE_STACK_SPEC.md` і §8.6.  
- **Шар G — Генерація варіантів.** Синтетичні аліаси (орфо/фонетичні/транслітераційні/клавіатурні) для відомих канонічних назв. *Підхід: BUILD (техніка; post-MVP, болгаро-важкий — §9.3).*

- Дає: глобальну таксономію видів, наукові назви, синоніми, ієрархію.  
- Доступ: API \+ дамп. Ліцензія: CC0 / CC-BY (підтвердити версію за конкретним релізом). Комерція: так. Source-ID: `col_id`.

**World Flora Online (WFO)** — шар A.

- Дає: таксономію рослин, WFO-ID, синонімію. Доступ: дамп/DOI. Ліцензія: CC-BY/CC0 (підтвердити). Комерція: так. Source-ID: `wfo_id`.

**GBIF Backbone Taxonomy** — шари A, B.

- Дає: уніфікований таксономічний бекбон \+ частину народних назв (`vernacularNames`). Доступ: API (`api.gbif.org`) \+ bulk-дамп. Ліцензія: CC0/CC-BY (окремі набори можуть бути NC — **відфільтрувати некомерційні**). Комерція: так (для CC0/CC-BY-частини). Source-ID: `gbif_taxon_key`.  
- Примітка: uk/bg-покриття вернакуляру часткове — доповнюємо EPPO/Wikidata/локалізацією.

**Ukraine State Register of Plant Varieties (Держреєстр сортів)** — шар C. **\[верифіковано\]**

- Дає: \~14 000 офіційно зареєстрованих сортів культур з українськими назвами (точний обсяг уточнити — у джерелах розбіжність 13 790 / 14 776).  
- Поля схеми (verbatim, datapackage): `taxonName`, `сountryCode`*, `groupRipeness`, `varietyNameLan` (латиниця), `plantPatent`, `dateApplication`, `applicationNumber`, `varietyName` (кирилиця), `varietyNameTRL` (транслітерація), `taxonGroupName`, `proposedZone`, `taxonGroupNameEn`, `publicDomain`, `taxonNameLat`, `startDateRegistration`, `directionUse`, `quality`, `creationMethod`, `сountryCodeApplicant`*, `taxonNameEn`. Плюс ресурси `VarietisOwners`, `VarietisMaintainers`.  
- *Гача даних:* у назвах колонок `сountryCode` і `сountryCodeApplicant` перша літера — кирилична «с» (U+0441), не латинська «c». Парсер має це врахувати.  
- Доступ: завантаження CSV/XLSX (data.gov.ua, dataset `ccf95f4a-...`; дзеркало minagro). Ліцензія: **CC BY 4.0 International (verbatim)**, комерція дозволена **з обов'язковим посиланням на джерело**. Source-ID: `applicationNumber` \+ `register_resource_id`.  
- *Застереження (з верифікації):* (1) головний CSV віддається як `octet-stream` — на білді завантажувати нормальним HTTP-клієнтом/браузером, не покладатися на проблемний фетчер; (2) `robots.txt` забороняє ботів — тягнути конкретні resource-URL разово, не краулити портал; (3) портал сам позначив датасет «Не оновлений» попри дату 2025-07-15 і місячну періодичність — звіряти актуальність на білді.

**Wikidata** — шари B, E (доповнення).

- Дає: частину культиварів і багатомовних назв. Доступ: SPARQL \+ дампи. Ліцензія: CC0. Комерція: так. Source-ID: `wikidata_qid`.  
- Примітка: покриття UA/BG плямисте — лише як доповнення, не основне джерело.

**Vertebrate Breed Ontology (VBO)** — шар D. **\[верифіковано\]**

- Дає: \~20 473 терми (породи хребетних \+ імпортований каркас), стабільні VBO-ID, вирівняно на NCBITaxon (види) і DAD-IS (FAO). Версія 2026-04-15.  
- Доступ: завантаження obo/owl/json (PURL → GitHub raw). Ліцензія: **CC BY 4.0 (verbatim)**, дозволяє адаптацію \+ редистрибуцію з атрибуцією. Комерція: так (з атрибуцією). Source-ID: `vbo_id`.  
- *Застереження:* (1) мови — **лише англійська** (`languages:["en"]`); 0 uk / 0 bg / 0 кирилиці — uk/bg-мітки додаємо самі; рідні назви присутні лише як романізована латиниця (напр. «Sira Ukrainska») — використати як старт для зворотної транслітерації в кирилицю; (2) **лише хребетні** — бджіл/Apis нема (поза скоупом онтології); (3) \~20k термів містять імпортований каркас — відфільтрувати підмножину власне порід.

**Open-source інструменти двигуна (шари F/G)** — увесь стек permissive, self-host, $0 ліцензій. Ядро: Meilisearch (MIT), ICU/PyICU (Unicode), cyrtranslit (MIT) \+ translit-ua (MIT), RapidFuzz (MIT), Splink (**MIT — підтверджено**), string\_grouper (MIT), jellyfish (**BSD-2**, не MIT). Повний перелік із ліцензіями й призначенням — `MATCHING-ENGINE_STACK_SPEC.md`. **Пастка «дані≠код»:** ліцензію вшитих датасетів/ваг перевіряти окремо від ліцензії коду (підтверджений випадок: Augmentex код MIT, але дані KartaSlov — CC BY-NC-SA, некомерційні; брати рушій, не дані).

## §7. Модель даних (схема)

Реляційна модель. Усі первинні ключі — внутрішні стабільні UUID (наші, незалежні від джерел). ID джерел зберігаються як окремі поля для ре-синку й провенансу. Формат опису: `поле` (тип, обов'язковість) — опис.

### §7.1. Сутність `Taxon` (вид/таксон — шар A/B)

Призначення: бекбон видів, до яких прив'язуються сорти/породи.

- `taxon_id` (UUID, обов'язк.) — внутрішній ключ.  
- `rank` (enum: kingdom…genus…species…subspecies, обов'язк.) — таксономічний ранг.  
- `scientific_name` (text, обов'язк.) — латинська наукова назва.  
- `parent_taxon_id` (UUID, опц.) — батьківський таксон (ієрархія).  
- `status` (enum: active | synonym | deprecated, обов'язк.) — статус таксону.  
- `accepted_taxon_id` (UUID, опц.) — якщо synonym, посилання на прийнятий таксон.  
- `source_id` (FK→Source, обов'язк.) — первинне джерело.  
- `gbif_taxon_key` (text, опц.), `col_id` (text, опц.), `wfo_id` (text, опц.), `ncbitaxon_id` (text, опц.), `eppo_code` (text, опц.) — ID джерел (join-ключі для ре-синку).  
- `created_at`, `updated_at`, `last_synced_at` (timestamp).

### §7.2. Сутність `CatalogItem` (сорт або порода — шари C/D)

Призначення: уніфікований запис культивара (variety) або породи (breed) під таксоном. Дискримінатор `kind` розрізняє вид\-специфічні поля.

- `item_id` (UUID, обов'язк.) — внутрішній ключ; головний join-ключ для об'єктів журналу.  
- `kind` (enum: variety | breed, обов'язк.) — тип запису.  
- `taxon_id` (FK→Taxon, обов'язк.) — вид, до якого належить.  
- `canonical_display_name_id` (FK→Name, обов'язк.) — посилання на канонічну назву показу за замовчуванням (мова — за §12).  
- `status` (enum: provisional | confirmed | merged | deprecated, обов'язк.) — стан життєвого циклу (§11).  
- `merged_into_id` (UUID, опц.) — якщо merged, посилання на канонічний запис-наступник.  
- `origin` (enum: official\_register | vbo | manual\_seed | user\_created | agent\_proposed, обов'язк.) — походження.  
- `registration_status` (enum: registered | landrace | unknown, обов'язк.) — офіційний статус сорту/породи.  
- `locale_scope` (enum/array: ua | bg | both | global, обов'язк.) — до якої локалі належить (звідки прийшов; не зливати UA/BG).  
- `popularity_count` (int, default 0\) — кількість об'єктів/логів, що посилаються (для м'якої канонізації ранжуванням).  
- Source-ID за `kind`: `register_application_number` \+ `register_resource_id` (variety, UA); `iasas_ref` / `eu_catalogue_ref` (variety, BG); `vbo_id` \+ `dad_is_ref` (breed).  
- breed-специфічні (опц., з VBO/DAD-IS): `breed_distribution` (enum: local | transboundary | national\_population), `species_group` (text).  
- `created_by` (FK→User, опц.) — хто створив (для UGC; персональні дані — §13).  
- `verified_by` (FK→User, опц.), `verified_at` (timestamp, опц.) — хто/коли підтвердив.  
- `created_at`, `updated_at`, `last_synced_at` (timestamp).  
- `canonical_form` (text, обов'язк., **UNIQUE-індекс у межах taxon+locale**) — нормалізована канонічна форма для апаратної гарантії проти точних дублів (§8.4). Обчислюється з канонічної назви через конвеєр §8.1.

### §7.3. Сутність `Name` (канонічна назва або аліас — шари B/E; серце entity resolution)

Призначення: усі назви (канонічні показу \+ аліаси/синоніми \+ орфо-варіанти), прив'язані до Taxon або CatalogItem. Typeahead і fuzzy-match працюють саме по цій сутності.

- `name_id` (UUID, обов'язк.).  
- `owner_type` (enum: taxon | catalog\_item, обов'язк.) — до чого прив'язано.  
- `owner_id` (UUID, обов'язк.) — посилання на власника (Taxon або CatalogItem).  
- `text` (text, обов'язк.) — назва як є (для показу).  
- `normalized_text` (text, обов'язк., індекс) — нормалізована форма для матчингу (§8.1): NFC, lowercase/casefold, складено кириличні варіанти (ё/е, и/і, ґ/г, апострофи) через ICU \+ власний fold-шар, прибрано пунктуацію.  
- `translit_key` (text, обов'язк., індекс) — **бієктивний транслітераційний (латинський) ключ** (ISO-9 через cyrtranslit/iso9 або ICU `Cyrillic-Latin`), обчислюється на вході; спільний ключ для крос-абеткового пошуку/матчингу (uk↔ru↔bg↔latin). Консистентний, не обов'язково стандарт-конформний (для офіційної латинки показу — окремо, translit-ua/власна BG-таблиця).  
- `phonetic_key` (text, опц., індекс; **post-MVP**) — фонетичний ключ (ru — fonetika; uk/bg — власні правила, §9.3/прогалини). Для зв'язування співзвучних різнонаписаних назв.  
- `locale` (enum: uk | ru | bg | en | la, обов'язк.) — мова назви.  
- `script` (enum: cyrillic | latin, обов'язк.) — графіка.  
- `role` (enum: canonical\_display | alias | misspelling\_variant | scientific | romanized, обов'язк.) — роль назви.  
- `source_id` (FK→Source, обов'язк.) — звідки назва (register | vbo | eppo | wikidata | manual\_seed | user | generated).  
- `status` (enum: confirmed | provisional, обов'язк.) — підтверджено чи в черзі.  
- `created_at`, `verified_at` (timestamp).  
- Обмеження: для одного CatalogItem може бути кілька `canonical_display` (по одному на локаль) \+ багато `alias`. `normalized_text`/`translit_key` не унікальні глобально (різні сутності можуть мати схожі назви), але дублі в межах одного власника усуваються; апаратна гарантія проти точних дублів — `CatalogItem.canonical_form` UNIQUE (§7.2, §8.4).

### §7.4. Сутність `Source` (реєстр джерел \+ база провенансу)

Призначення: довідник усіх джерел даних \+ правова метаінформація. Кожен Taxon/CatalogItem/Name посилається сюди.

- `source_id` (slug, обов'язк.) — напр. `ua_state_register`, `vbo`, `gbif`, `col`, `wfo`, `eppo`, `wikidata`, `iasas`, `eu_catalogue`, `dad_is`, `manual_seed`, `user`, `agent`, `generated`.  
- `name` (text), `url` (text), `version_or_snapshot` (text) — версія/знімок завантаження.  
- `license` (text, обов'язк.) — ідентифікатор ліцензії (CC0 / CC-BY-4.0 / MIT / conditional / …).  
- `license_url` (text), `license_text_verbatim` (text) — дослівний текст (для умовних/CC-BY).  
- `commercial_allowed` (bool, обов'язк.), `redistribution_allowed` (bool), `attribution_required` (bool), `attribution_text` (text).  
- `access_method` (enum: api | download | parse\_pdf | manual | ugc), `last_sync_at` (timestamp).  
- Примітка: запис `iasas` має містити дослівну підставу дозволу (§5.2).

### §7.5. Сутність `MergeLog` (аудит злиттів — недеструктивно)

- `merge_id` (UUID), `from_item_id` (FK→CatalogItem), `into_item_id` (FK→CatalogItem), `merged_at`, `merged_by` (FK→User), `reason` (text), `affected_object_count` (int).  
- Логіка злиття (§8.4): `from_item.status=merged`, `from_item.merged_into_id=into_item`; канонічна назва `from_item` стає `alias`\-Name на `into_item`; об'єкти журналу перенаправляються на `into_item`. Нічого не видаляється.

### §7.6. Сутність `CurationReview` (черга курування)

- `review_id` (UUID), `target_type` (enum: catalog\_item | name | merge\_candidate), `target_id` (UUID).  
- `kind` (enum: new\_item | new\_alias | merge\_candidate), `status` (enum: pending | approved | rejected | merged).  
- `suggested_match_id` (UUID, опц.) — кандидат-збіг (від fuzzy/dedup).  
- `submitted_source` (enum: user | agent), `created_at`, `reviewed_by`, `reviewed_at`.

### §7.7. Точка стику з продуктом

- `JournalObject.catalog_item_id` (FK→CatalogItem) — об'єкт користувача (його помідор/вулик) посилається на запис каталогу. Це з'єднання й створює соцграф «усі, хто веде цей сорт». Повна модель об'єкта — у продуктовій спеці; тут фіксуємо лише зв'язок і те, що `popularity_count` рахується з цих посилань. Крім FK на каталог, об'єкти й записи беруть участь у графі `Edge` (§7.10) — крос-юзерні провенанс/референс/згадка/follow-зв'язки; публічний рендер цих ребер — сорт-медіаційний (`CROSS_USER_TRUST_AND_PRIVACY_SPEC_v0.md §3`), з повагою-видимості (§2 там само).

### §7.8. Ключі та провенанс (зведено)

- Внутрішні UUID — стабільні, наші, незмінні при ре-синку.  
- Source-ID кожного джерела зберігаються окремими полями (§7.1–§7.2): `gbif_taxon_key`, `col_id`, `wfo_id`, `ncbitaxon_id`, `eppo_code`, `wikidata_qid`, `vbo_id`, `dad_is_ref`, `register_application_number`, `iasas_ref`, `eu_catalogue_ref`. **Це обов'язково:** без них ре-синк і звірка з оригіналом неможливі.  
- Ключі матчингу на `Name`: `normalized_text` \+ `translit_key` (обов'язкові) \+ `phonetic_key` (post-MVP) — живлять §8. Апаратна гарантія дедупу — `CatalogItem.canonical_form` UNIQUE.
- Нові сутності крос-шару: `User` (§7.9; `user_id`, `handle` UNIQUE) і `Edge` (§7.10; `edge_id`, поліморфні `source`/`target`, `state`). `Edge.state {proposed|confirmed|declined}` — окремий простір від каталогових `status`-enum'ів.

### §7.9. Сутність `User` (ідентичність користувача) [ADD 2026-06-21]

Призначення: формалізує ідентичність, на яку вже посилаються FK (`created_by`/`verified_by`/`merged_by`/`reviewed_by`), і яка стає ТЕГОВАНОЮ через @-хендл (крос-юзерний шар). Псевдонімна, без PII (`OverGarden_B2_METRICS_v0.md §3`).

- `user_id` (UUID, обов'язк.) — внутрішній ключ.
- `handle` (text, обов'язк., **UNIQUE**) — @-хендл; публічний тегований ідентифікатор.
- `display_name` (text, опц.) — показове ім'я.
- `status` (enum: active | pending, обов'язк.) — `pending` = стаб-ідентичність від інвайту не-юзера (ще не приєднана); → `active` при приєднанні+claim (`CROSS_USER_TRUST_AND_PRIVACY_SPEC_v0.md §4`).
- `created_at` (timestamp).
- Приватність — §13 (псевдонімність; `handle` публічний, решта за налаштуваннями користувача).

### §7.10. Сутність `Edge` (крос-юзерне / крос-сутнісне ребро) [ADD 2026-06-21]

Призначення: поліморфний зв'язок між контентом автора й ціллю — провенанс-лінія, референс сорту, @-згадка, follow. Семантика згоди / поваги-видимості / сорт-медіації — `CROSS_USER_TRUST_AND_PRIVACY_SPEC_v0.md` §1–§4; тут лише поля схеми.

- `edge_id` (UUID, обов'язк.).
- `edge_type` (enum: provenance | reference | mention | follow, обов'язк.) — `provenance`=лінія-герой («походить від X»); `reference`=вказівка на сорт/каталог-вузол; `mention`=@-згадка в body; `follow`=соц-підписка.
- `source_type` (enum: entry | object, обов'язк.) — звідки ребро (запис/об'єкт автора).
- `source_id` (UUID, обов'язк.).
- `target_type` (enum: object | space | user | catalog_item | entry, обов'язк.) — поліморфна ціль (`LINEAGE_SOCIAL_GRAPH_SPEC_v0.md §6`).
- `target_id` (UUID, обов'язк.).
- `state` (enum: proposed | confirmed | declined, обов'язк.) — стан згоди ребра. **Увага: НЕ плутати** з каталоговим `confirmed | provisional` (`CatalogItem.status §7.2`, `Name.status §7.3`) — інша семантика (згода крос-юзер, не курування каталогу).
- `respect_visibility` (bool, default true) — рендер клампиться до рівня видимості цілі (для крос-юзер завжди true; `CROSS_USER_TRUST_AND_PRIVACY_SPEC_v0.md §2`).
- `created_by` (FK→User, обов'язк.), `created_at` (timestamp).
- `confirmed_by` (FK→User, опц.), `confirmed_at` (timestamp, опц.), `declined_at` (timestamp, опц.).
- Інвайт не-юзера (pending-ціль): `target_type=user` + `target_id`→`User` зі `status=pending`; ребро `proposed` НЕ зливає нічого до приєднання+claim (`CROSS_USER_TRUST_AND_PRIVACY_SPEC_v0.md §4`).

## §8. Entity resolution та дизайн матчингу (шар F)

Вибір і конфігурація інструментів — `MATCHING-ENGINE_STACK_SPEC.md`. Тут — як двигун лягає на модель даних. Платформа конвеєра — **Python worker-first** (увесь стек Python-нативний; matching/dedup/reindex off-request-path; Meilisearch — окремий сервер по HTTP, derived index).

### §8.1. Нормалізація назв і ключі (на вході й при сіді)

Кожна `Name.text` проходить конвеєр:

1. **Нормалізація → `normalized_text`:** Unicode NFC → casefold → **власний доменний шар складання кириличних варіантів** (ё↔е, и↔і, ґ↔г, варіанти апострофа) поверх ICU `Transliterator`/`gennorm2` → видалення пунктуації/зайвих пробілів. *Складання РІЗНИХ літер жоден інструмент не робить «зі стандарту» — це власна крихітна доменна мапа (закладено як окрему роботу).*  
2. **Транслітераційний ключ → `translit_key`:** бієктивний ISO-9 (cyrtranslit/iso9 або ICU `Cyrillic-Latin`) — спільний латинський ключ для крос-абеткового матчингу.  
3. **Фонетичний ключ → `phonetic_key` (post-MVP):** ru — fonetika; uk/bg — власні правила.

Зберігати всі обчислені ключі для пошуку/матчингу.

### §8.2. Typeahead (вибір зі списку — первинний шлях вводу)

- Користувач друкує → запит нормалізується → пошук по `Name.normalized_text` (+ за потреби `translit_key`) через Meilisearch (typo-tolerant, prefix-search, кирилична токенізація Charabia).  
- Результати ранжуються за: (а) якістю збігу, (б) `CatalogItem.popularity_count` (популярніше — вище → м'яка канонізація), (в) локаллю користувача.  
- Показується **канонічна назва власника** збіглого Name; користувач тапає → об'єкт прив'язується до `CatalogItem`.
- Межа індексу: Postgres — source of truth; Meilisearch — derived index. Тільки worker-owned indexer пише в Meili; app/features пишуть у Postgres і читають Meili для typeahead/search (`TECH_STACK_DECISIONS §2.7`; `MATCHING-ENGINE_STACK_SPEC §6 A`).

### §8.3. Гейт створення нового запису

1. Перед створенням — fuzzy-match (RapidFuzz; за потреби збіг по `translit_key`) нової назви проти наявних `Name`.  
2. Якщо є збіги вище м'якого порога — показати «Це воно?» зі списком кандидатів; вимагати явного «жодне з них», щоб продовжити.  
3. Справді новий → `CatalogItem` зі `status=provisional`, `origin=user_created|agent_proposed` → запис у `CurationReview`.  
4. Пороги — параметри, що **калібруються емпірично** (не фіксуємо наперед); калібрування — на **обов'язковому PoC** (`MATCHING-ENGINE_STACK_SPEC.md` §11) і метриках §11.4.

### §8.4. Дедуп і злиття

- **М'який дедуп (батч):** **Splink** \+ **string\_grouper** (n-gram TF-IDF — практичний для коротких назв) \+ **RapidFuzz**\-гейт; перед матчингом — **крок транслітераційної нормалізації** (через `translit_key`); **фонетичні рівні Splink вимкнути** (англо-орієнтовані). Кластеризує provisional \+ near-duplicate записи → кандидати на злиття в `CurationReview`. (Третя опція — recordlinkage, BSD-3.)  
- **Апаратна гарантія (твердий дедуп):** **UNIQUE-індекс по `CatalogItem.canonical_form`** (у межах taxon+locale) — не дає створити точний дубль канонічної форми на рівні БД.  
- **Крос-абетковий матч** (щоб «Воловье сердце» зливалося з «Бичаче серце» через спільний запис) — через `translit_key`/`phonetic_key` \+ RapidFuzz (DIY-конвеєр, §8.7), не окремий інструмент.  
- Злиття — **недеструктивне** (§7.5): об'єкти перенаправляються, дубль-назва стає аліасом, нічого не видаляється. Раннє «сміття» відновлюване.

### §8.5. М'яка канонізація популярністю

Ранжування typeahead за `popularity_count` робить так, що запис, який обрали 50 людей, виринає над одруківкою однієї. Лінь користувача тоді працює на збіжність. (Слабко на \<100 користувачів — рання фаза тримається на сіді \+ founder-куруванні, §11.)

### §8.6. Стек інструментів (що / для чого)

MVP-мінімум позначено ★; решта — post-MVP (повний опис «що/як/для чого» — `MATCHING-ENGINE_STACK_SPEC.md` §6).

- ★ **Meilisearch** (MIT) — derived typeahead-пошук з typo-tolerance \+ кирилична токенізація \+ ранжування за популярністю; записи в індекс ідуть тільки через single worker/indexer. *(Альт. за глибшої морфології — OpenSearch, Apache 2.0.)*  
- ★ **ICU/PyICU** (Unicode) \+ **власний fold-шар** — нормалізація `normalized_text`.  
- ★ **cyrtranslit** (MIT) — `translit_key`; **translit-ua** (MIT) — офіційна романізація показу (uk КМУ-2010 \+ ru); болгарська Streamlined — власна таблиця.  
- ★ **RapidFuzz** (MIT, Unicode по code points) — схожість рядків (гейт «це воно?», гейт дедупу). Доповнення: textdistance (MIT), jellyfish (BSD-2); **pg\_trgm** у БД-шляху — **обов'язково UTF-8 locale БД** (інакше кирилиця ламається).  
- ★ **UNIQUE-індекс по `canonical_form`** — апаратна гарантія проти точних дублів.  
- **Splink** (MIT) \+ **string\_grouper** (MIT) — пакетний дедуп; фонетичні рівні вимкнути.  
- **fonetika** (MIT, ru) \+ власні правила (uk/bg) — `phonetic_key` (post-MVP, прогалина — §14).

### §8.7. Крос-мовний матч імен (C2 — власний конвеєр, post-MVP)

Зрілого permissive-інструмента, що трактує крос-абеткові варіанти імені «як єдине ціле» з доказовою кирилицею, **немає** (підтверджено обома deep-research прогонами). Тому:

- **Будуємо власний конвеєр:** `translit_key` (B2) \+ `phonetic_key` (B3) \+ RapidFuzz/pg\_trgm (C1). UA≠RU≠BG моделюємо як поле/блокуючий ключ самі.  
- **Платне (Senzing та ін.) НЕ беремо** — виправдано лише за enterprise-масштабу й слабше на болгарській.  
- **Шлях DIY** (правила vs ембединги LaBSE/e5) — вирішує **PoC** на реальних кириличних парах (`MATCHING-ENGINE_STACK_SPEC.md` §11).

## §9. Конвеєр сіду (ETL)

### §9.1. Загальні принципи

- **Ідемпотентність:** повторний запуск не дублює (матч за source-ID).  
- **Провенанс:** кожен запис стемпиться `source_id` \+ source-record-ID \+ `version_or_snapshot` \+ `ingested_at`.  
- **Дедуп при сіді:** нові назви матчаться проти наявних перед вставкою (§8.3 без UI-гейта — автоматично, з логом неоднозначностей на ручний рев'ю); обчислюються `normalized_text`/`translit_key` (§8.1).  
- **Логування:** кожен крок пише лог (скільки додано/оновлено/пропущено/конфліктів).

### §9.2. Порядок сіду

1. **Видовий кістяк (шар A):** CoL/WFO/GBIF → `Taxon` (наукові назви, ієрархія, source-ID).  
2. **Вернакуляр видів (шар B):** EPPO \+ Wikidata \+ GBIF vernacular → `Name` (owner=taxon, locale uk/bg/ru). Прогалини — у власну локалізацію.  
3. **Сорти UA (шар C):** Держреєстр CSV → `CatalogItem` (kind=variety) \+ `Name` (canonical uk з `varietyName`, alias latin з `varietyNameLan`, romanized з `varietyNameTRL`); прив'язка до `Taxon` через `taxonNameLat`. Врахувати гачу кириличної «с» у назвах колонок.  
4. **Сорти BG (шар C):** IASAS PDF-парсинг \+ EU-каталог → `CatalogItem` \+ `Name` (canonical bg \+ latin).  
5. **Породи (шар D):** VBO (відфільтрувати підмножину порід) → `CatalogItem` (kind=breed) \+ `Name` (canonical en, romanized-аліаси); зворотна транслітерація romanized → кандидати uk/bg-міток (на верифікацію). Бджоли/нехребетні — ручний список (звірений з DAD-IS).  
6. **Ручний засів аліасів голови (шар E):** топ-100–200 поширених культур → LLM пропонує набір синонімів (uk/ru/bg/орфо) для відомого канонічного сорту → людина звіряє → `Name` (alias, source=manual\_seed, status=confirmed). *Це закриває холодностартову прогалину: typeahead працює з дня 1 для найпопулярнішого.*

### §9.3. Генерація варіантів (шар G; post-MVP, болгаро-важкий)

Для кожної канонічної назви — згенерувати правдоподібні варіанти написання й заіндексувати їх **як синоніми канонічного запису в Meilisearch** (щоб typeahead упізнавав їх без окремого матч-проходу). Конвеєр (`MATCHING-ENGINE_STACK_SPEC.md` §6 B5):

- **Оркестрація примітивів:** транслітерація (B2: cyrtranslit/translit-ua) \+ фонетика (B3: fonetika ru; uk/bg власні) \+ клавіатурні помилки (B4: nlpaug `uk.json` для uk; Augmentex-рушій для ru; **bg — власна БДС-мапа через clavier**) \+ **Norvig-`edits`\-генератор з кириличним алфавітом**.  
- **Фільтр:** усе пропускається через **RapidFuzz** (відсікти неправдоподібне) → `Name` (role=misspelling\_variant, source=generated).  
- **🚩 Пастка даних:** Augmentex — брати **рушій, не вшиті дані** (KartaSlov \= CC BY-NC-SA, некомерційні).  
- **Обмеження:** генерувати лише варіанти ВХІДНОГО рядка (не вигадувати нові назви); стежити за колізіями з іншими сортами.  
- **Прогалини (build):** uk/bg фонетика й болгарська розкладка — готового немає, будувати власне (§14; `MATCHING-ENGINE_STACK_SPEC.md` §12).

## §10. Механізм оновлення та обслуговування

### §10.1. Дві моделі (не одна)

- **Кістяк \+ офіційні списки (шари A/C/D-офіційне):** майже статика; планове оновлення.  
- **Аліаси/хвіст (шари E \+ UGC):** безперервний ріст через користувачів \+ курування.

### §10.2. Плановий ре-синк офіційних джерел

- Розклад: за періодичністю джерела (Держреєстр — щомісяця; EU/VBO/CoL — за релізами).  
- Процес: завантажити свіжий знімок → diff проти збереженого за source-record-ID → застосувати додавання/зміни → **ніколи не hard-delete**: знятий з реєстру сорт → `status=deprecated`, лишається в БД (люди досі його вирощують) → лог diff → оновити `version_or_snapshot` і `last_synced_at`.  
- Конфлікти (зміна назви/таксона вгорі) → у `CurationReview`, не авто-перезапис.

### §10.3. Ріст хвоста (UGC) \+ курування

- Користувацькі/агентські записи → provisional → черга → підтвердження/злиття.  
- Тіри курування: **founder з дня 0** (обсяг малий) → \+ м'яка канонізація популярністю (1k–5k) → \+ волонтерське курування (5k+).

### §10.4. Агент як недовірене джерело

Якщо вмикається агент, що пропонує нові записи (для довгого хвоста чи аліасів) — він **проходить той самий гейт**, що й користувач: `submitted_source=agent`, `status=provisional`, dedup-перевірка, людська верифікація. **Ніколи не авто-додає й не авто-зливає.** Для офіційних джерел агент не потрібен — там детермінований ре-синк (§10.2).

### §10.5. Реконсиляція

Збережені source-ID дають змогу перез'єднати записи, якщо вгорі змінюються ідентифікатори чи структура. Без них — ручний біль; тому source-ID обов'язкові (§7.8).

## §11. Якість даних і governance

### §11.1. Політика канонічної назви

- Для офіційних сортів канонічна — офіційна назва з реєстру (uk для UA, bg для BG).  
- Канонічна показу може бути по одній на локаль (§12).  
- Зміна канонічної — лише через курування (з логом).

### §11.2. Політика аліасів

- Аліас — будь-який підтверджений варіант: інша мова, регіональний, романізований, поширена одруківка (role=misspelling\_variant, нижчий пріоритет показу).  
- Аліаси не показуються як окремі записи в typeahead — вони ведуть до канонічного.

### §11.3. Життєвий цикл статусу (стан-машина)

`provisional` → (курування) → `confirmed` ; `confirmed`/`provisional` → (злиття) → `merged` ; офіційний, знятий з реєстру → `deprecated`. Жоден перехід не видаляє дані.

### §11.4. Метрики здоров'я каталогу

- **Частка сортів-одинаків** (CatalogItem з popularity\_count=1) — індикатор фрагментації; зростає → збіжність провалюється.  
- **Кількість near-duplicate пар** у черзі — навантаження дедупу.  
- **% provisional** від загалу — борг курування.  
- **Час у черзі** курування; **rate злиттів**. Ці метрики — також орієнтир для калібрування порогів §8.3 (разом із PoC).

### §11.5. Аудит і провенанс

Кожен запис має простежуване джерело (§7.4) \+ дату інжесту/верифікації; кожне злиття залоговане (§7.5). Це закриває вимогу верифікованості й полегшує юридичний аудит (доказ, що комерційні дані — лише із зеленої зони).

## §12. Локалізація

- Мови: uk, ru, bg, en, la. Графіки: cyrillic, latin.  
- **Канонічна показу — per-locale:** один `CatalogItem` може мати `canonical_display` Name для uk і окремий для bg (обидва role=canonical\_display, різні locale) \+ спільні аліаси. Користувачу показується канонічна його локалі; якщо нема — fallback (en/la \+ аліас).  
- **VBO-локалізація:** VBO дає en-назву \+ романізований синонім; ми створюємо uk/bg `Name` (canonical\_display), використовуючи романізований синонім як старт для зворотної транслітерації \+ ручну звірку.  
- **Крос-мовний матчинг:** через `translit_key` (+ `phonetic_key` post-MVP) — щоб «Воловье сердце» (ru) знаходило `CatalogItem` з канонічною «Бичаче серце» (uk) через спільний аліас (DIY-конвеєр §8.7). Офіційна романізація показу — translit-ua (uk/ru) \+ власна BG-таблиця.  
- **Розділення локалей:** `CatalogItem.locale_scope` фіксує походження (UA-реєстр vs BG-реєстр); UA і BG дані не зливаються в звітності й курування ведеться окремо. **Болгарська — найслабша мова двигуна** (фонетика, розкладка, транслітерація) — закладати окремий бюджет (§14).

## §13. Приватність і відповідність (GDPR / DSA)

- **Каталожні дані — неперсональні факти** (назви видів/сортів/порід). Зберігання й комерційне використання — за ліцензіями §6.  
- **Персональні дані виникають у зв'язках:** `CatalogItem.created_by` / `verified_by`, `Name` (хто додав), `MergeLog.merged_by`, об'єкти журналу. Це проєктується за **GDPR Art. 25 (privacy by design/default)**.  
- **Право на стирання vs недеструктивне злиття:** при запиті на стирання — видаляється/анонімізується **зв'язок користувача** (`created_by` → null/anonymized), а сам каталожний запис (факт-назва) лишається, бо він неперсональний і потрібен для цілісності соцграфа. Це сумісно: стираємо персональну атрибуцію, не факт.  
- **Публічний UGC:** оскільки модель продукту — публічний індексований UGC, дані, що стають публічними, не повинні містити персональних даних понад те, на що користувач погодився. Атрибуція внеску — за згодою.  
- **BG/EU — пряма дія GDPR/DSA/AI Act** (зона Block 22): юридичний рев'ю обов'язковий перед запуском у BG.  
- **Атрибуція джерел (CC-BY)** не є персональними даними — це окрема вимога §6.2.

## §15. Глосарій

- **Канонічна назва (canonical)** — основна назва запису для показу (per-locale).  
- **Аліас (alias)** — додатковий варіант назви (інша мова/регіон/написання), що веде до канонічного запису.  
- **Таксон (Taxon)** — вид/рід тощо (бекбон).  
- **Сорт (variety/cultivar)** — культурний різновид рослини.  
- **Порода (breed)** — різновид тварини.  
- **Entity resolution / зведення** — приведення різних написань тієї самої сутності до одного запису.  
- **`normalized_text`** — нормалізована форма назви для матчингу (NFC, casefold, складена кирилиця, без пунктуації).  
- **`translit_key`** — бієктивний латинський (ISO-9) ключ назви; спільний ключ для крос-абеткового матчингу.  
- **`phonetic_key`** — фонетичний ключ назви (за звучанням; post-MVP).  
- **`canonical_form` (UNIQUE)** — нормалізована канонічна форма запису; апаратна гарантія проти точних дублів.  
- **Провенанс** — простежуване походження запису (джерело \+ версія \+ дата).  
- **Source-ID** — ідентифікатор запису в зовнішньому джерелі (join-ключ для ре-синку).  
- **Недеструктивне злиття** — об'єднання дублів без видалення: перенаправлення посилань \+ дубль-назва стає аліасом.  
- **Provisional / «непідтверджено»** — статус нового запису до людської верифікації.  
- **Permissive / копілефт** — permissive (MIT/BSD/Apache/ISC/Unicode/PostgreSQL) можна вбудовувати в закритий комерційний продукт; копілефт (GPL/LGPL/AGPL/SSPL) — ні.  
- **Пастка «дані≠код»** — ліцензія коду й ліцензія вшитих даних/ваг можуть різнитися; перевіряти окремо.  
- **Sui generis database right** — окреме (від копірайту) право ЄС на вкладення в компіляцію бази; захищає від вилучення суттєвої частини.  
- **CC0 / CC-BY / MIT** — вільні ліцензії: CC0 (public domain), CC-BY (з атрибуцією), MIT (permissive для софту).  
- **Шари каталогу (A–G)** — A: види · B: вернакуляр видів · C: сорти · D: породи · E: аліаси сортів · F: двигун зведення · G: генерація варіантів.
