## ПУНКТ №1 — Акаунти / авторизація / легальні сторінки — **ЗАКРИТО 2026-06-23**

**Статус канонізації:** `PENDING-КАНОНІЗАЦІЇ` — реальна зміна скоупу (нові MVP-фічі поза `PRD §2/§11` і `Бізнес §11.1`); change-set у канон — у кінцевому заході, авторизація оператора отримана в сесії.

### Рішення

**1.1. Акаунт-система — обов'язкова.** Моат (публічний мережевий шар: @-хендли, соцграф, провенанс-атрибуція, follow, claim-inbox, GDPR-видалення акаунта) структурно вимагає сталої ідентичності. Не предмет дебатів; вирішено архітектурою. _(FarmVi-модель «нуль реєстрації» свідомо відхилена як несумісна з тезою.)_

**1.2. Auth-gating: гість-читає-все, акаунт-на-будь-яку-дію-запис.** Гість має повний READ-доступ до всіх публічних поверхонь (сторінки-записи, сторінки-сорти, регіон/проблема/тематичні, профілі, граф-родовід, коментарі, блог) — нуль акаунта. Акаунт потрібен на будь-яку дію, що створює стан, прив'язаний до ідентичності: створення простору / об'єкта / запису; коментарі (топ-рівень + відповіді); закладки; follow; wishlist; @-теги; claim/confirm.

**1.3. ВИНЯТОК — лайк без акаунта; [ПЕРЕПИСАНО 2026-09-04] але вже не «один на пристрій і косметичний».** Лайк — постійний рядок з рівно одним власником: `user_id` для залогіненого, `visitor_id` для гостя (одна підписана site-wide кука, що з'являється в мить першого лайку й переноситься на акаунт при реєстрації). Без стелі, без терміну життя, обидві половини рахуються публічно; у ранжуванні читатиметься лише `user_id`-половина (ADR-0024 D1). Історичне рішення: один на людину через локальний функціональний токен, тогл. **Косметичні — НІКОЛИ не годують ранжування / видимість / фід-порядок / популярність** (гардрейл). «Один на людину» — М'який, не жорсткий: витоки (кілька пристроїв; очищення сховища / інкогніто) приймаються як косметичні. Rate-limit per IP/device — обов'язковий (анти-спам/DoS на неавтентифікованому ендпойнті). _(Провенанс-виправлення: попередня прив'язка лайків до `AC-INV4` була нестрогою — `AC-INV4` стосується lineage-ребер, не лайків.)_

**1.4. [ПЕРЕПИСАНО 2026-09-04] СТІНИ З ПРОНОСОМ ЧЕРНЕТКИ НЕМАЄ.** Чернеток немає взагалі, тож проносити нічого; вхід відбувається на одному екрані `/auth/sign-in`, а `?next=` повертає читача туди, звідки він прийшов (для наміру «новий запис» — прямо до композера). Історичне рішення: стіна тригериться на «Зберегти», гість складає запис, чернетка проноситься крізь auth-флоу. Механізм: commitment-and-consistency + endowment — цінність показана до прохання закомітитись.

**1.5. Методи входу — [ПЕРЕПИСАНО 2026-09-04] РЕАЛІЗОВАНО ДВА:** пошта (email/пароль) + Google. Facebook відкликано в коді (`src/lib/auth/retired-social-provider.ts`), Apple ніколи не реалізовували. Історичне рішення 2026-06-23 називало всі чотири.

**1.6. Легальні сторінки — у канон як MVP-блокери:** privacy policy, terms of service, видалення акаунта (+ cookie-consent — див. 1.7). Мінімальні, простою мовою, НЕ enterprise-legalese. _(Корпусна підпора: `ONLYFARMERS_FINAL` Картка 2 «legal-first» BUILD + Картка 3 «довіра правилами» — рамку правил у першу версію MVP. Мітигація скептика — мінімалізм копі.)_

**1.7. Cookie-стратегія — варіант C:** стандартний GA4 + cookie-consent-банер. Повна аналітика; consent-management-платформа (CMP) + банер потрібні. _(Оператор обрав C над рекомендованим B (cookieless). Трейд: повна GA4-fidelity для живого WATCH H1/H4/H6 ↔ банер-фрикція на вході acquisition-воронки + CMP-оверхед. Зафіксовано.)_

## ПУНКТ №2 — Публічні агрегації (колапс таксономій B5 ↔ Бізнес) — **ЗАКРИТО 2026-06-23**

**Статус канонізації:** `PENDING-КАНОНІЗАЦІЇ` — реконсиляція `B5 §2` ↔ `Бізнес §10.14` (формалізація шва, не правка жодного); сурфейсить нову ADMIN/курація-поверхню (вже потрібну за S7).

### Рішення

**2.1. ОДИН агрегаційний двигун + типовані фасети + теги-як-резолюція (НЕ spawning).** Спільна інфраструктура, що НЕ дублюється per-тип: thinness-гейт + index-промоція, SSR/пре-рендер, внутрішня перелінковка, дедуп майже-дублів, замок локації, schema.org, пагінація.

**2.2. Фасети (ключі НЕ косметичні — різна сутність/джерело/канонізація):**

- **Сорт** ← `CatalogItem` (дедуп-safe, `canonical_form` UNIQUE). `[MVP]`
- **Регіон** ← грубий регіон (замок локації). `[Ф2]`
- **Проблема** ← курований діагностичний концепт (курований сет). `[MVP]`
- **Курована тема/категорія** ← курований сет (Овочі / Ягоди / Квіти / Кімнатні рослини / Балконний город / Компост / Теплиці). **Поглинає Бізнес тематичні + категорії.** Побутові назви, НЕ наукові. `[MVP]`
- **Крос** ← перетини (сорт×регіон, сорт×проблема, проблема×регіон). Demand-gated. `[Ф2]`
- **Таксон/вид** ← `Taxon` — **ВНУТРІШНІЙ бекбон, публічно НЕ виставляється** (Q1-рішення: аматор шукає «Томати», не «Solanum lycopersicum»). `[внутр.]`

**2.3. Теги = routing-шар, НЕ page-spawning** ([ПЕРЕПИСАНО 2026-09-04]: сама ідея тега-як-резолюції жива, але «вільний тег → `noindex` без URL» замінено на «вільний тег просто не створює сторінки»). Тег резолвиться в фасет (збіг з `CatalogItem`→сорт; курована тема→тема; курована проблема→проблема). Вільний юзер-тег без курованої цілі → `noindex`, без публічного URL. Прямий захист проти `§6` thin-page-explosion. Наслідок: «Томати» сорт = тег = тематична = **ОДНА сторінка**, нуль канібалізації.

**2.4. Курування = ВАРІАНТ A (повністю куровано) + АСИСТ [рішення оператора].** Лише оператор заводить, які категорії/теми існують. **ДОДАНО:** курація-асист — популярні юзер-теги сурфейсяться ранжовано за частотою; оператор ОДНІЄЮ дією промоутить популярний тег у куровану категорію/тему. **КЛЮЧОВО — промоція лишається ДЕЛІБЕРАТИВНИМ едиторським актом, НЕ авто-поріг** (це і відрізняє від варіанта B: B = авто-промоція за порогом без людини; тут = людина бачить підказку й вирішує). Гейт ручний → thin-content вибуху немає.

**2.5. Хаби/гайди — окремий тип** (едиторські статті, hand-written, cold-start-ядро); ділять патерн «курований топ + UGC-низ» з тема-сторінкою; можуть ділити шаблон через параметр content-weight (article-heavy ↔ aggregation-heavy). Спорідненість зафіксована, злиття не форсовано.

### Наслідки для дерева (застосувати при регенерації)

- `A2–A6` колапсують в ОДИН двигун з фасет-enum; `A6` (тематична/тег/категорія) поглинається як фасет «курована тема» + механізм тег-резолюції; `A7` (хаб/гайд) лишається. Менше окремих шаблонів, один thinness-гейт, нуль дублів.
- **НОВА ЗОНА (раніше пропущена в дереві v0, але вже потрібна за S7):** **Admin / Curation поверхня** — курація-дашборд, що містить: (1) **каталог-черга курування** (provisional `CatalogItem` від user-add + нові аліаси + merge-кандидати — `DB_SEED §7.6 CurationReview` / §8.3; вже в MVP-скоупі через `S7`/`AC-S7`); (2) **популярні-теги-промоція-черга** (новий, з 2.4). Для solo-founder — може бути мінімальний внутрішній адмін-інструмент, не полірована продуктова сторінка, але це поверхня в інвентарі.
- Вид-сторінки (`Taxon`) — НЕ публічні (внутрішній бекбон).

### Дані (мала добавка, не нова система)

- **Tag-frequency count** — ранжувати популярні теги для курація-дашборду. Розширює наявну `CurationReview` + `popularity_count` інфру.

### Відкрите

- **Thinness-гейт поріг** (N записів / текст-обсяг для index-промоції) — емпірична прогалина (`B5 §9`); пост-лонч тюнінг, не вирішується в чаті/спеці зараз.

## ПУНКТ №3 — Модал-vs-маршрут (класифікація флоу-поверхонь) — **ЗАКРИТО 2026-06-23**

**Статус канонізації:** `PENDING-КАНОНІЗАЦІЇ` — класифікаційне рішення; застосовується до тегів типу поверхні в дереві при регенерації.

### Рішення

**3.1. ПРАВИЛО — share-test.** Маршрут (власний URL) = поверхня, на яку має сенс скинути посилання, АБО destination, де лишаєшся (back-button семантика). Модал/аркуш = транзитна дія, що спливає й повертає тебе в контекст. _(На мобілці «модал» = повноекранний аркуш, що повертає назад — не обов'язково мале віконце; за змістом усе одно модал.)_

**3.2. РЕДАКТОР запису = ВАРІАНТ A; [ПЕРЕПИСАНО 2026-09-04] ЧЕРНЕТОК НЕМАЄ.** Редактор — композер на сторінці об'єкта й окремий маршрут редагування `/garden/entries/[entryId]/edit`. Опублікований запис має URL (`A1`, ним діляться). Списку чернеток не існує: незбережений текст живе в пам'яті вкладки. _(Чернетки приватні → SEO не торкається → URL на чернетку = функція без вжитку; A — стандарт мобільних композерів.)_

**3.3. КЛАСИФІКАЦІЯ (застосувати до тегів типу в дереві):**

- **МАРШРУТИ:** усі публічні сторінки (`A*`), профіль (`A8/C3`), граф-родовід (`A9/C2`), домівка (`B0`), фід (`B0b`), екран простору (`B1`), екран об'єкта (`B2`), журнал/деталь-запису (`B4`), публічна сторінка-запис (`A1`), claim-inbox (`C1`), wishlist-полиця (`D1`), пошук (`B6`), блог (`E*`), налаштування (`F6` + суб-маршрути), auth-сторінки (`F1–F5`), легальні/статичні (`G*`), інвайт-лінк-лендинг (`C4.1`), **адмін/курація** (нова зона з №2), **список чернеток** (приватний маршрут, як налаштування).
- **МОДАЛИ/АРКУШІ:** створити/редагувати простір (`B1.1`), створити/редагувати об'єкт (`B2.1`), **редактор запису + space-story композер** (`B1.2/B3`, варіант A — повноекранні аркуші, transient, без URL), backdating-пікер (`B3.3`), location-override (`B3.5`), first-publish disclosure (`B3.7` — інлайн у save), save→progress (`B3.8` — транзитний стан/оверлей, НЕ маршрут), confirm/decline тег (`C1.1`), ask-the-lineage композер (`C2.2`), block/report (`C3.2`), інвайт-складання (`C4`), add-to-wishlist (`D1.1`), діалог лайка, контекстний auth-модал (з №1).

### Наслідки для дерева

- Кожен лист отримує точний тег типу: `(маршрут)` / `(модал)` / `(аркуш)` / `(стан)` / `(дія)` за класифікацією 3.3.

- _(post-MVP)_ `/en/` `/ro/` `/tr/`

[ПЕРЕПИСАНО 2026-09-04] **Реалізовано інакше — ринок-перший:** Україна лише `uk` на неперфіксованих URL, Болгарія `bg` (дефолт) і `ru`. Українська в BG і російська в UA як публічні канонічні набори — скасовані (OVE-205). Історичне формулювання: **hreflang ТІЛЬКИ-МОВНИЙ** (`uk`/`ru`/`bg`, НЕ `uk-UA`/`ru-BG`), бо рос. і укр. тепер охоплюють ОБИДВА ринки (рос. — і в UA, і в BG; укр. — і в UA, і серед переселенців у BG); лише болгарська одно-регіональна. Language-only hreflang валідний (таргетує мову глобально) і ТОЧНІШИЙ під крос-країнну аудиторію. Папка `uk` (НЕ `ua`): `ua` не валідний код мови (ISO 639-1 української = `uk`). **«Ринок» виходить з URL** — geo-IP/Accept-Language на корені визначає дефолт + сет перемикача; регіон контенту = ГРУБИЙ регіон об'єктів/агрегацій (не папка). x-default → `/uk/` (або root-picker).

_(REVISED: попередня карта `uk-UA`/`bg-BG`/`ru-BG` — одна мова на ринок — СУПЕРСЕДНУТА рішенням оператора 2026-06-23; тепер кожна мова спанить ринки, тег language-only.)_

**Чому НЕ region-first** (`/ua/uk/`, `/bg/ru/`…): 5 локаль-регіон-папок = більше build; виправдано лише якщо потрібен per-country SEO-таргет І аудиторія не спанить країни — жодне не тримається (регіон content-driven; аудиторія крос-країнна). Відхилено.

**4.3. [REVISED 2026-06-23] Доступність мов per ринок (runtime default + market-filtered switcher):**

- **UA-ринок** (geo=Україна): [ПЕРЕПИСАНО 2026-09-04] **лише українська, без префікса**; мовного вибору немає.
- **BG-ринок** (geo=Болгарія): [ПЕРЕПИСАНО 2026-09-04] default **болгарська** `/bg`; вибір — **російська** `/ru`. Української в наборі BG немає.

Default визначає geo-IP/Accept-Language на корені `over.garden/` → редірект у дефолтну папку ринку. Switcher market-filtered (показує сет ринку). **Російська на launch (ОБИДВА ринки) — channel-validated:** укр. переселенці + російськомовні в BG (оператор має owned-канал); рос. у UA — частина старшої ЦА. (ro/tr/en — post-MVP.) Болгарська — лише BG (одно-регіональна).

**4.4. UGC НЕ перекладається.** Запис існує однією мовою автора; hreflang-кластеризація стосується chrome + агрегацій + едиторіалу, НЕ сирих тіл записів. Каталог готовий: `Name.locale` має `ru`; `CatalogItem.locale_scope` розділяє UA/BG (`DB_SEED §7.2/7.3`).

- **НОВА поверхня: перемикач мови — у ОБОХ ринках** (UA: uk⇄ru; BG: bg⇄ru⇄uk), market-filtered. _(REVISED — було «лише BG».)_ Живе в налаштуваннях + ймовірно в хедері.

### Уточнення / прапори

- **Крос-скрипт матчинг (РЕКОМЕНДОВАНО-ТАК, не page-tree рішення):** UA-матчинг приймає російський ввід як пошуковий аліас («помидор»→«помідор»). Уже design каталогу (`translit_key`; `MATCHING §10`). Деталь матчинг-спеки.

## ПУНКТ №5 — Видалення → 410 + родовід-entanglement + erasure-on-request — **ЗАКРИТО 2026-06-23**

**Статус канонізації:** `PENDING-КАНОНІЗАЦІЇ` — заповнює прогалину (`Edge §7.10` не мав on_delete-поведінки; `AC-S9d` не торкався лінійних ребер). Знімає юрисдикційну ставку.

### Рішення

**5.1. 410 Gone (НЕ 404)** для видаленої публічної сторінки → швидша де-індексація. Наскрізний СТАН КОЖНОГО `{SSR}`-вузла, НЕ окрема сторінка. `AC-S9d`.

**5.2. Родовід-entanglement = ВАРІАНТ A (анонімізувати-зберегти-ребро), застосовується ЗА ЗАПИТОМ на стирання** (НЕ авто при видаленні акаунта). Особу+PII стираємо (обличчя на фото, ім'я в тексті, точна локація, хендл, email); структурні лінійні ребра лишаються **анонімними надгробками** («походить від колишнього гровера [сорту]»). Анонімізація має бути СПРАВЖНЯ — незворотна, без re-identification (k-anonymity: у рідкій зоні «сорт+регіон»→одна особа — прибираємо й регіон, лишаємо сам сорт). Рів (мережа/провенанс/агрегації) збережений; втрачається лише атрибуція, НЕ контент.

**5.3. Модель видалення (3 рівні):**

- **Видалення ЕЛЕМЕНТА** (запис/об'єкт/простір/журнал) → **Архів/Кошик** (soft-delete, recoverable); публічна видимість зникає **НЕГАЙНО** (410+де-індексація) навіть поки в архіві; архів приватний. Grace ~30 днів → жорстка чистка.
- **Видалення АКАУНТА** → акаунт закрито; прямі ідентифікатори (email/хендл) відв'язано/анонімізовано **НЕГАЙНО**; контент лишається анонімним (рів); UI **ЯВНО** пропонує повне видалення.
- **Запит на СТИРАННЯ** → застосувати A (PII геть, ребра-надгробки) → дані стерто, не зберігаємо.

**5.4. Erasure-on-request, ОДНАКОВО UA+BG.** GDPR НЕ вимагає авто-видалення при close-акаунта; вимагає виконати запит Art.17 коли надходить. **Знімає юрисдикційну ставку** (попередній прапор «GDPR дотягується до UA-юзерів бо оператор BG-established» + «UA-закон дає erasure-право» → МООТ: обидва ринки = однакова erasure-on-request логіка, без розгалуження по юрисдикції).

**5.5. Чотири умови (БІНДЯТЬ патерн):**

1. Реагувати на запит ≤30 днів; потрібен канал (форма/email) + процес.
2. Стирання СПРАВЖНЄ (A) коли спрацьовує.
3. «Видалив-акаунт ≠ стер-дані» — **ЯВНО в UI** (прозорість; інакше GDPR-порушення + брендова катастрофа).
4. При close-акаунта — відв'язати прямі ідентифікатори (email/хендл) **одразу**, навіть якщо контент лишається.

### Наслідки для дерева (застосувати при регенерації)

- **НОВА поверхня: Архів/Кошик** (приватний маршрут) — soft-deleted елементи (записи/об'єкти/простори/журнали), recoverable.
- **НОВА поверхня: «Запит на видалення даних»** (форма; у налаштуваннях `F6` + privacy policy `G2`).
- **Флоу видалення акаунта** (`F6.7`): close → відв'язка ідентифікаторів → ЯВНИЙ UI з пропозицією повного стирання.
- **410-стан** на КОЖНОМУ `{SSR}`-вузлі (`A1–A9`, `E*`, профілі).
- **Перерахунок агрегацій:** видалення записів може опустити сторінку-сорт/крос нижче thinness-гейту → пере-оцінка index-статусу (`§6`-захист).

### Відкрите / юр

- Юрист підтверджує ДРІБНИЦЮ: формулювання erasure-on-request + строк + відповідність Art.17 (НЕ фундаментальний конфлікт — вирішено). Лягає в той самий Art.6 юр-рев'ю.
- AI-краулер/LLM де-індексація — **best-effort** (не можна стерти з натренованої моделі); ЯВНО розкрити в privacy policy (`AC-S9d` це визнає).

## ПУНКТ №6 — Спільні вузли (профіль, граф) — **ЗАКРИТО 2026-06-23**

**Статус канонізації:** `PENDING-КАНОНІЗАЦІЇ` — дедуплікує дерево; підтверджує SEO-таксономію `B5` (профіль/граф НЕ в рову).

### Рішення

**6.1. Профіль `@-хендла` = ОДИН вузол, публічно-видимий але NOINDEX.** `A8` (публічний SSR) зливається в `C3` (соц-вузол). Видно людям + shareable лінком (вийшов-із-акаунту бачить), Google НЕ індексує. Причина: ~нуль пошукового попиту на псевдонімні хендли + індексація ВСІХ профілів = `§6` thin-content кара. Афордменти умовні за станом: вийшов-із-акаунту (публічне) / залогінений-на-чужому (+follow, block, ask-the-lineage) / залогінений-на-своєму (+редагування, доступ до чернеток/архіву/налаштувань).

**6.2. Граф-родовід = ДВА шари:**

- **Індексований провенанс-ПІДСУМОК** — СЕКЦІЯ на сторінці-сорті (`A2.2`, вже там — Флоу17) + на екрані об'єкта (`B2.2`). Це SEO-видиме.
- **Повний інтерактивний граф** («N людей, M країн, одне насіння» + ask-the-lineage) = окремий **NOINDEX** інтерактивний в'ю (`C2`; ask-the-lineage за стіною). Окремої індексованої сторінки-графа НЕМАЄ. `A9` зливається.

**6.3. Документація:** ОДИН документ на кожен спільний вузол (профіль, граф), з відмітками обох контекстів (публічно-видимий бік + автентифіковані афордменти). Дублювати = ризик дрейфу двох описів однієї сторінки.

### Наслідки для дерева (застосувати при регенерації)

- `A8` → зливається в `C3` (профіль, noindex).
- `A9` → зливається: провенанс-підсумок = секція на `A2`/`B2`; повний граф = `C2` (noindex). Окремого індексованого `A9` немає.
- [ПЕРЕПИСАНО 2026-09-04] **«Публічно-видимий але `noindex`» більше не валідний стан вузла.** Усе живе публічне індексується, профіль і повний граф зокрема. `noindex` лишився для порожнього списку, семиденного `410` і воркспейсу.

### Підтверджує

- `B5` SEO-таксономія: рів = сорт/проблема/регіон/крос/хаб; профіль/граф НЕ пошукові поверхні.
