## Why This Exists

Linear `Done` is not enough for OverGarden. During the 2026-06-29 audit, OVE-29 and OVE-30 had valid branch closeout comments, but those branch commits were not contained in the `main` checkout that the next agent would use. That creates a worse product risk than an ordinary missing feature: every later slice can be built on a false baseline.

This guard makes the next-agent starting point explicit:

1. Read this document.
2. Start from a Git-clean `main` (no tracked or non-ignored untracked delta) and fast-forward normally. The guard verifies that `origin` is the canonical `yehor-design/over.garden` repository, performs its own non-interactive, 30-second-bounded `git fetch --no-tags origin +refs/heads/main:refs/remotes/origin/main`, and fails if that fetch cannot prove freshness or if `HEAD` differs from the newly fetched ref. Ignored build/cache outputs are outside the cleanliness gate.
3. Run `cd apps/web && pnpm mainline:closeout:check`.
4. Only continue to the next Linear issue when every repository-changing prerequisite is contained in current `origin/main`; required live behavior additionally has exact-contained-SHA deployment/provider proof. An external-state-only prerequisite instead needs an explicit no-repository-delta declaration and immutable provider receipt.

## Closeout Rule For Future Issues

Every future Linear work item must leave the closeout evidence required by its issue contract and `docs/LINEAR_AI_EXECUTION_TASK_STANDARD.md`. A feature-branch SHA alone is not proof. If repository content changed, the implementation commit must be contained in current `origin/main`; a deployment is additional behavior proof and never substitutes for repository containment. An external-state-only operator task that produces no repository delta uses an explicitly identified provider receipt as its terminal source of truth. A non-executable coordination container closes only from independently completed child contracts, an acyclic relation read-back, and its own integration acceptance receipt; it creates no branch or provider effect.

Required closeout evidence:

- Linear issue id and title.
- Repository change: implementation commit SHA contained in current `origin/main`.
- Production behavior: deployment/provider receipt for that contained exact SHA, when applicable.
- External-state-only task: explicit no-repository-delta statement plus immutable provider/action receipt, environment identity, read-back, and rollback/cleanup result.
- Coordination container: explicit zero-own-implementation declaration, complete child identifiers and relations, acyclic DAG proof, every child independently `Done`, integration acceptance receipt, and terminal Linear state read-back.
- Branch/ref used for proof, or `Not applicable — no repository delta` with the unchanged baseline SHA.
- For repository changes, main containment proof, for example:

```bash
git branch --contains <completed-issue-sha>
git merge-base --is-ancestor <completed-issue-sha> HEAD
git merge-base --is-ancestor <completed-issue-sha> origin/main
```

- Verification commands/read-back operations that passed.
- CI run URL for the contained commit when repository content changed; external-state-only work instead records the exact existing-control/provider proof receipt, and coordination records child/integration receipts.
- Deployment id, public URL, and redacted smoke evidence when the issue touches live production behavior.
- A statement that no secrets, invite URLs, journal text, media keys, raw request metadata, live user identifiers, or precise location data were included in the evidence.

Use this Linear closeout template:

```markdown
Mainline closeout:

- Issue:
- Commit contained in origin/main, or no-repository-delta declaration:
- Ref/branch:
- Containment proof:
- Local verification:
- CI/deployment proof:
- Child DAG/integration receipt, for coordination only:
- Live smoke proof, if relevant:
- Redaction/privacy note:
```

## Failure Gates

Do not mark a Linear issue `Done` when any of these are true:

- A repository-changing task cites only a feature-branch commit that is not contained in verified current `origin/main`.
- A repository-changing fix is not contained in verified current `origin/main`, or required live behavior lacks deployment/provider proof for that contained exact SHA.
- A repository-changing proof omits CI/build status for the exact baseline the next agent will use; an external-state-only or coordination closeout omits its applicable provider/child/integration read-back.
- Live smoke evidence includes secrets, invite URLs, raw journal content, media storage keys, exact location, raw request metadata, emails, IP addresses, user agents, or user identifiers.
- The next agent can still follow stale roadmap/status text into an older execution batch instead of the current Linear queue.

## Ledger Maintenance

`docs/mainline-closeout-ledger.json` tracks critical closeout entries that must be machine-checked before the next agent continues. It is intentionally small; it is not a full release log.

Add or update a ledger entry when:

- A recently completed issue is a blocker for the next Linear slice.
- A prior closeout was proven only on a branch and later receives a superseding `main` commit.
- A contained production deployment receipt becomes a required prerequisite for later repository work.

Schema v2 of the ledger tracks repository-changing entries only. Every row is a current prerequisite, must set `requiredForNextSlice: true`, is structurally and containment-validated, and belongs to the pinned required-issue inventory in the checker; non-prerequisite history does not belong in this ledger. `updatedAt` and `completedAt` are real, non-future `YYYY-MM-DD` calendar dates in the project timezone `Europe/Sofia`. `verificationCommands` preserves at least two non-trivial commands declared by the historical closeout, but it is not an immutable execution receipt and is never treated as a substitute for authenticated CI/deployment read-back.

The normal proof commit is `mainCommit`. A different `proofCommit` is exceptional: it must pair with `proofCommitReason: closeout_only_descendant`, be the single-parent direct child of `mainCommit`, and change only `docs/MAINLINE_CLOSEOUT.md` and/or `docs/mainline-closeout-ledger.json`. This narrowly represents a closeout-only deployment child without allowing later product code to stand in for the declared behavior commit.

`ciRunUrl` is either the exact numeric run URL under `https://github.com/yehor-design/over.garden/actions/runs/` or the exact provider-console deployment URL under `https://vercel.com/yehors-projects-01221e2b/over-garden/`; provider roots, unrelated projects, non-run/deployment slugs, and nested job pages are invalid. An Actions row is accepted only after an authenticated API read proves the canonical repository, exact run id/URL, exact proof SHA, `completed/success`, workflow id `302590914`, name `CI`, path `.github/workflows/ci.yml`, and allowed `push` or `workflow_dispatch` event. A Vercel row must additionally store positive `githubDeploymentId` and `githubDeploymentStatusId` receipts. Authenticated GitHub Deployments read-back must prove that exact deployment id, SHA and ref equal to the proof commit, task `deploy`, `Production` environment/original environment, canonical `vercel[bot]` identity, and the declared latest status id. The latest status must be `success` in `Production`, owned by the same app, and expose one identical immutable OverGarden Vercel app URL as its environment, target, and log URL. A newer non-success status, missing/malformed response, id/SHA/ref drift, or timeout fails closed. The Vercel console URL remains provider provenance; it is never trusted by shape alone.

The CI job runs `pnpm mainline:closeout:check`, which first requires a Git-clean worktree, verifies canonical `origin`, and explicitly fetches `origin/main` with a pinned refspec, non-interactive credentials, and a 30-second timeout. It fails closed when that fetch is unavailable or the checkout is stale: local `main` must equal the newly fetched `origin/main`. Pull-request mode is accepted only for the `yehor-design/over.garden` GitHub Actions repository when checked-out `HEAD` exactly equals the 40-character `GITHUB_SHA` event revision and contains the newly fetched base. It then verifies every schema-v2 ledger row is required, structurally valid, uniquely present in the pinned prerequisite inventory, contained in both checked-out `HEAD` and `origin/main`, and backed by authenticated exact-SHA outcome read-back. Every GitHub API request has a 30-second deadline; all row reads run concurrently and any rejection fails the batch. Local execution uses `GH_TOKEN`/`GITHUB_TOKEN` or a bounded `gh auth token` fallback. CI injects `${{ github.token }}` explicitly, grants `deployments: read` plus the existing Actions/content scopes, and bounds the web, matching, and matching-image jobs to 60, 30, and 60 minutes respectively. The ledger has no queue field: authenticated Linear is the primary execution queue, and this file is only a repository/deployment prerequisite ledger. Version 2 supersedes schema v1, which allowed deployed-commit-only status and carried an unused top-level queue field. External-state-only operator and coordination receipts remain in their validated Linear closeout until a future ledger schema represents their environment/digest or child-DAG semantics without pretending they are Git commits.
